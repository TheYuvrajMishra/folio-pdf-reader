# Spike S1 — Headless pdf.js engine (WebView) : raster + text lines

**Status:** complete (M0). **Date:** 2026-10-17. **Agent:** S1.
**Question:** can pdf.js run headless in a WebView, fully offline, rasterizing pages
and extracting per-item text geometry fast enough for the Folio reader?

## 1. Bundling decision (offline pdf.js)

**Approach:** esbuild-bundle `pdfjs-dist/legacy/build/pdf.mjs` (main-thread build) to
a single minified IIFE (`globalName: pdfjsLib`); ship
`pdfjs-dist/legacy/build/pdf.worker.min.mjs` as the worker source string.

- Legacy build chosen deliberately: ES5-ish output, no top-level await, widest
  Android System WebView compatibility. No CDN anywhere — everything inlined.
- Script: `scripts/bundle-pdfjs.mjs`. It validates: both outputs parse
  (`node --check`); the main bundle executes in a bare `vm` context and exposes
  `pdfjsLib.getDocument`; main/worker version+build stamps agree
  (**6.4.299 / d0991a0d5** — pdf.js refuses mismatched worker builds at runtime);
  the inlined strings round-trip byte-identical (sha256) into
  `src/engine/html/bootstrap.generated.ts`.
- `src/engine/html/bootstrap.ts` is the template (placeholder constants);
  the bundler replaces them and writes `bootstrap.generated.ts`, which exports
  `buildEngineHtml()` — the full engine HTML with both bundles inlined.
  Re-run the bundler after any pdfjs-dist upgrade. `PdfEngine` imports the
  generated module.

**Sizes (pdfjs-dist 6.4.299):**

| artifact | bytes |
|---|---|
| main bundle (`assets/pdfjs/pdf.main.bundle.js`) | 528,864 (516.5 KB) |
| worker source (`assets/pdfjs/pdf.worker.bundle.js`) | 1,321,307 (1290.3 KB) |
| **total inlined** | **1,850,171 (~1.77 MB)** |
| generated HTML (bundles + bootstrap) | ~1.86 MB |

1.8 MB of inline JS is acceptable for M0: it lives in one HTML string built once
at engine start, no network, no disk reads on the hot path.

**Worker instantiation:** at runtime the bootstrap creates
`URL.createObjectURL(new Blob([workerSrc], {type:'text/javascript'}))` and sets
`pdfjsLib.GlobalWorkerOptions.workerSrc` to it; pdf.js 6.x then does
`new Worker(url, {type:'module'})` itself. Because the page origin is opaque
(`about:blank` for injected HTML), pdf.js takes its built-in `_createCDNWrapper`
path — wrapping the blob URL in an `await import("<blob>")` blob — still fully
offline. If worker creation ever fails, pdf.js falls back to its main-thread
fake worker automatically (no crash). **M1 must verify the blob worker actually
spawns on-device** (the Node bench can't — see §4).

## 2. Transfer decision (PRD §7.3): (b) chunked base64, primary

**Decision: (b) chunked base64 (512 KB chunks) into a preallocated `Uint8Array`
inside the WebView as the primary path; (a) `file://` URL as the large-file
path (> 64 MB); (c) native fallback unchanged (see §5).**

Research from the installed `react-native-webview@14.0.1` source
(`RNCWebViewManagerImpl.kt ::createViewInstance`):

- Android defaults are now **hardened**: `allowFileAccess=false`,
  `allowContentAccess=false`, `allowFileAccessFromFileURLs=false`,
  `allowUniversalAccessFromFileURLs=false`,
  `mixedContentMode=MIXED_CONTENT_NEVER_ALLOW`. Props exist to re-enable each.
- Path (a) would require `allowFileAccess={true}` +
  `allowFileAccessFromFileURLs={true}` on the engine WebView **and** loading the
  bootstrap HTML itself from a `file://` URL (an `about:blank` page fetching
  `file://` is blocked), plus uncertainty about XHR range-request support on
  `file://` URLs across Chromium versions. It works, but it widens the file-read
  capability of a JS context and has the most OEM/Chromium variance.
- Path (b) works with **every default left hardened** — zero native flags, zero
  attack-surface change, deterministic on all API levels. Cost is transient
  memory: file bytes + ~33% base64 during transfer, so it is gated:
  **≤ 64 MB → chunked path; > 64 MB → path (a)** with file access enabled only
  on the headless engine WebView (which loads no remote content), where pdf.js
  fetches the `file://` URL itself (`open-url` request).
- Never one giant message: `PROTOCOL_CHUNK_BYTES = 512*1024` both directions
  (PDF in, raster out). The RN side should stream chunks from disk
  (`expo-file-system` chunked base64 read, M1) so the whole file never sits in
  the RN JS heap either.

Protocol: `src/engine/protocol.ts` — typed requests
(`open-begin/open-chunk/open-end`, `open-url`, `render-page`, `get-lines`,
`get-outline`, `close`, `ping`), per-request `id` echoed by responses,
unsolicited `ready` / `open-progress` events, `unknown`-narrowing guards at the
bridge boundary (no `any`).

## 3. Engine scaffold (`src/engine/`)

| file | what |
|---|---|
| `html/bootstrap.ts` | template: placeholder constants + `buildEngineHtml()` + the WebView-side engine JS (open/render/get-lines/get-outline/close over the protocol, chunked I/O, worker-blob setup) |
| `html/bootstrap.generated.ts` | generated (do not edit): same module with real bundles inlined; what `PdfEngine` imports |
| `protocol.ts` | typed wire protocol + guards |
| `PdfEngine.ts` | class wrapping react-native-webview: `getWebViewProps()` (hardened headless props), ref attach, serial job queue, per-request timeouts, `ready` gating, chunked `openBytes()`, `openUrl()` (large-file path), `renderPage()`, `getLines()`, `getOutline()`, `close()`, render-process-death counting per PRD §7.9 |
| `base64.ts` | pure-TS base64 encoder (Hermes has no `Buffer`) |

**Deviation from PRD §7.4 found during the spike:** `viewport.convertToViewportRectangle()`
does not exist in pdf.js 6.4.299 (removed; only `convertToViewportPoint`
remains). The engine implements the equivalent by transforming the item's four
corners — origin plus width/height along the *normalized* transform axes (item
width/height are in user-space units while the transform axes carry font-size
scale; forgetting the normalization produced garbage rects, caught and fixed
against the rotated fixture page) — via `convertToViewportPoint`, then min/max
and normalize by viewport size. Verified on the fixture: rotated-page items
produce tall narrow boxes (x 0.149–0.170, correct for 90° text); normal items
match expected positions (e.g. heading at x0=0.105 = 64/612 pt).

## 4. Benchmarks (Node proxy — NOT device numbers)

`scripts/spikes/s1/bench.mjs` runs the **legacy** build in Node against
`assets/test-fixtures/folio-test.pdf` (10 pages, 7,950 bytes, real selectable
text incl. an empty page and a 90°-rotated page). Canvas via `@napi-rs/canvas`
with the canvas-factory pattern pdf.js needs outside a browser (documented in
the script header). In Node pdf.js disables its worker (main-thread fake
worker), so this is a **pessimistic single-thread proxy**; on-device numbers
(real worker thread, Android WebView) deferred to M1/APK.

Machine: this VM (Linux x86_64, 2 vCPU, 8 GB), Node v24.20.0.

| op | p50 | p95 | mean | n |
|---|---|---|---|---|
| engine init (`getDocument` parse) | — | — | **382.8 ms** | 1 doc |
| text extract / page (`getTextContent`) | 3.97 ms | 26.79 ms | 10.66 ms | 30 |
| render @1x / page (warm) | 9.38 ms | 51.10 ms | 15.25 ms | 30 |
| render @2x / page (warm) | 6.10 ms | 28.32 ms | 8.19 ms | 30 |
| render @1x / page (**cold**, the prefetch case) | 14.22 ms | 148.07 ms | 31.23 ms | 10 |
| peak RSS | **314 MB** (baseline node+imports 257 MB → render loop adds ~57 MB) | | | |

Notes:
- Text items carry `{dir, fontName, hasEOL, height, str, transform, width}` —
  everything PRD §7.4 needs. Fixture averages 9.9 items/page (pdf-lib emits one
  text op per `drawText` call; real books have far more, finer-grained items).
- The @2x < @1x inversion is a benchmark-ordering artifact (second render on the
  same page reuses the parsed operator list), not a claim about scale cost.
- Cold first-render p95 (148 ms) is the number to watch against the PRD budgets
  (first page < 700 ms cached / < 1.8 s fresh); warm re-renders are ~5–15 ms.
  Comfortable headroom on this VM; device TBD.
- pdf.js warns `standardFontDataUrl` is not provided (standard-14 fonts render
  via fallback). M1 follow-up: either inline `standard_fonts/` or accept
  fallback rendering — decided in M1 after visual check.

Raw results: `scripts/spikes/s1/results.json`.

## 5. Standing decisions recorded

- **PRD §7.7 raster fallback: CONFIRMED as standing.** If WebView raster exceeds
  **800 ms/page p50 on the target device**, write the small Expo native module
  (Kotlin, Android `PdfRenderer`) for rasterization and keep pdf.js for text
  lines only. No action now; the Node proxy is nowhere near the threshold, but
  only on-device measurement counts.
- **Transfer:** (b) chunked base64 ≤ 64 MB primary; (a) `file://` + scoped
  `allowFileAccess`/`allowFileAccessFromFileURLs` on the headless WebView only,
  for larger files; never whole-file base64 in one message.

## 6. Known limitations / M1 follow-ups

1. Blob-worker spawn verified only by code inspection, not execution — M1 must
   confirm `new Worker(blobUrl, {type:'module'})` + the `_createCDNWrapper`
   path works in the Android WebView (fallback to fake worker is automatic but
   slower).
2. `PdfEngine.openBytes()` takes `Uint8Array`; M1 should add `openFile()` that
   streams 512 KB base64 chunks from disk via `expo-file-system` so large PDFs
   never sit whole in the RN heap.
3. `standardFontDataUrl` not provided — decide in M1 (inline vs fallback).
4. `bootstrap.generated.ts` (~1.8 MB) is a build artifact: CI must run
   `node scripts/bundle-pdfjs.mjs` before `tsc`/build, or the generated file
   must be committed (coordinator's call).
5. Fixture text items are coarse (one per `drawText`); line-clustering
   heuristics (PRD §7.4 steps 2–4) belong to the reader/data layer, not this
   spike — the engine just ships raw items with correct boxes.
