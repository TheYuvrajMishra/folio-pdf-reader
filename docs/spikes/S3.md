# S3 — SQLite + FTS5 search backend (M0 spike)

**Status:** done (2026-10-17). **Decision:** search backend = **FTS5**, chosen per PRD §6.9
(`page_text USING fts5(book_id UNINDEXED, page UNINDEXED, text)`). FTS5 is compiled
into the SQLite bundled with expo-sqlite (Android + iOS), so no extension loading
and no extra dependency is needed.

## Decisions

1. **FTS5** as the full-text search backend (PRD §6.9). One row per page
   (`book_id UNINDEXED, page UNINDEXED, text`); query with `MATCH`, rank with
   the built-in `rank`. No trigram tokenizer needed for prefix search —
   `term*` covers the as-you-type case.
2. **WAL journal mode** (`PRAGMA journal_mode=WAL`) on open in `getDb()`, so the
   reader can read pages while the background indexer writes lines/FTS rows
   without locking each other out.
3. **Migrations via `PRAGMA user_version`**, versioned bodies in
   `src/data/migrations.ts`. v1 = full PRD §7.6 schema (books, reading_position,
   position_history, page_lines, page_text, annotations, annotation_ops,
   bookmarks, sessions, settings). Idempotent `IF NOT EXISTS` statements inside
   one transaction; `user_version` bumps only after commit.
4. **All writes for one user action in one transaction** (`withTransaction` in
   `src/data/db.ts`), e.g. annotation op row + materialized `annotations` row
   together — PRD §6.7.
5. Schema lives in `src/data/schema.ts` (`SCHEMA_STATEMENTS_V1` + indexes), so
   the benchmark, migrations, and any future tooling share one DDL source.
   Indexes: `page_lines(book_id,page,idx)` (ruler/resume lookups),
   `annotation_ops(book_id,seq)` (undo/redo), `annotations(book_id,page)`
   (page render), plus library/history/session indexes.

## What was built

- `src/data/schema.ts` — full CREATE TABLE / FTS5 / CREATE INDEX statements.
- `src/data/migrations.ts` — `runMigrations()`, `getSchemaVersion()`,
  `LATEST_SCHEMA_VERSION = 1`.
- `src/data/db.ts` — `getDb()` (lazy open + WAL + migrations, expo-sqlite
  `openDatabaseSync` SDK 58 API), `withTransaction()`, `closeDb()`.
  expo-sqlite is loaded via dynamic `import()` inside `getDb()` only — importing
  the module in Node (tests/benchmarks) does not crash; calling `getDb()` on a
  non-React-Native runtime throws a clear error.
- `scripts/spikes/s3/bench.mjs` — benchmark (better-sqlite3, FTS5).
- `npx tsc --noEmit`: no errors in `src/data/` (3 pre-existing scaffold errors
  in `src/components/*.web.tsx` / `src/constants/theme.ts`, untouched by S3).

## Benchmark results

Machine: Linux x86_64 sandbox VM, Node v24.20.0, better-sqlite3 13.0.3
(SQLite 3.53.4, FTS5 on). **Proxy only** — Node timing, not the Hermes/ARM
path of expo-sqlite; relative magnitudes are the signal. Corpus: synthetic
300-page book, 35 lines/page = **10,500 lines** deterministic English-like text
(mulberry32 seed 0xF0110), 300 FTS rows (one per page).

| Metric | Result |
|---|---|
| Insert 10,500 `page_lines` rows + 300 FTS rows (one txn) | **87.9 ms → ~119k lines/s** |
| DB size on disk (checkpointed, incl. FTS index) | **3.61 MiB** for the 300-page book |
| Single-term `MATCH` (200 queries) | p50 **0.33 ms**, p95 **0.42 ms** |
| Phrase `MATCH` (200 queries) | p50 **0.13 ms**, p95 **0.22 ms** |
| Prefix `MATCH 'abc*'` (200 queries) | p50 **0.35 ms**, p95 **0.52 ms** |
| `page_lines` point lookup — one page's 35 lines (200 queries) | p50 **0.03 ms**, p95 **0.04 ms** |

Sanity: `MATCH 'cache'` returns 268/300 pages — term frequencies behave like a
real technical book. As-you-type prefix queries and page-turn line lookups are
an order of magnitude under the 50 ms ruler-step budget (PRD §7.8); the whole
300-page index builds in < 100 ms of SQLite work (extraction dominates in
practice, that's the S1 spike's concern).

## Deferred / limitations

- **On-device expo-sqlite validation deferred to the APK.** These numbers come
  from better-sqlite3 on x86_64 Node. What still needs a real device: FTS5
  availability in the expo-sqlite bundled SQLite on the target Android build,
  WAL throughput on slow eMMC storage, and per-query latency under Hermes.
  Re-run `bench.mjs`'s corpus+queries against the device via a dev-build script
  before M5 (search ships P1).
- The `/tmp` on this VM is a 512M tmpfs at 100%; `bench.mjs` writes its scratch
  DB under `scripts/spikes/s3/.bench-tmp/` and removes it after the run.
- `page_text` is an external (non-`content=`) FTS5 table: the indexer must keep
  it in sync with `page_lines` (write both in one transaction; `withTransaction`
  helper exists for this). Deleted-page cleanup is a bulk `DELETE` per table.
- Benchmark query harness overhead (better-sqlite3 JS↔native call) is included
  in every sample; absolute numbers are upper bounds of SQLite cost.
- expo-sqlite API names verified from `node_modules/expo-sqlite@58.0.13`
  `build/SQLiteDatabase.d.ts`: `openDatabaseSync(name, options?, directory?)`,
  `execSync`, `getFirstSync`, `runSync`, `withTransactionSync/Async`.
